# Database Conventions — CloudNativePG (CNPG)

---

## What is CNPG

CloudNativePG is a Kubernetes operator that manages PostgreSQL clusters as first-class
Kubernetes resources. There is no standalone `postgres` container in this project — PostgreSQL
is always managed by the CNPG operator.

**Never reference generic PostgreSQL images or Docker postgres containers** in any spec,
manifest, or code outside of the CI pipeline (where a plain postgres container is acceptable
for unit integration tests only).

---

## Cluster Layout

Three CNPG clusters, one per jurisdiction. Each cluster is isolated — no shared storage,
no cross-cluster queries in the application layer.

| Cluster Name | Jurisdiction | AWS Region | Purpose |
|---|---|---|---|
| `stdclinic-ca` | Canada (QC) | `ca-central-1` | All CA patient data |
| `stdclinic-us` | United States | `us-east-1` | All US patient data |
| `stdclinic-br` | Brazil | `sa-east-1` | All BR patient data |

Each cluster runs:
- 1 primary + 2 read replicas (production)
- 1 primary + 1 replica (staging)
- 1 primary (local kind dev via CNPG operator)

## CNPG Cluster Manifest (template)

```yaml
# deploy/cnpg/cluster-ca.yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: stdclinic-ca
  namespace: std-data
spec:
  instances: 3
  primaryUpdateStrategy: unsupervised

  postgresql:
    parameters:
      max_connections: "200"
      shared_buffers: "256MB"
      pg_stat_statements.max: "10000"

  bootstrap:
    initdb:
      database: stdclinic
      owner: app
      secret:
        name: stdclinic-ca-app-secret

  storage:
    size: 100Gi
    storageClass: gp3

  backup:
    barmanObjectStore:
      destinationPath: s3://stdclinic-backups-ca/cnpg
      s3Credentials:
        accessKeyId:
          name: cnpg-s3-secret
          key: ACCESS_KEY_ID
        secretAccessKey:
          name: cnpg-s3-secret
          key: SECRET_ACCESS_KEY
      wal:
        compression: gzip
    retentionPolicy: "30d"

  monitoring:
    enablePodMonitor: true
```

## Connection Management

CNPG generates a Kubernetes Secret per cluster with connection credentials.
The application reads connection strings from environment variables injected from these secrets.

Environment variable names:

```
DATABASE_URL_CA     # postgresql://app:pass@stdclinic-ca-rw.std-data.svc/stdclinic
DATABASE_URL_US     # postgresql://app:pass@stdclinic-us-rw.std-data.svc/stdclinic
DATABASE_URL_BR     # postgresql://app:pass@stdclinic-br-rw.std-data.svc/stdclinic
DATABASE_URL_CA_RO  # read-only replica endpoint
DATABASE_URL_US_RO
DATABASE_URL_BR_RO
```

CNPG provides two services per cluster:
- `{cluster}-rw` — always points to the current primary (writes)
- `{cluster}-ro` — load-balanced across replicas (reads)

The `JurisdictionRouter` in `pkg/db/router.go` holds a pool for each and routes by jurisdiction.

### PgBouncer

CNPG's built-in PgBouncer pooler is used in transaction mode:

```yaml
# Add to cluster spec
  managed:
    roles:
      - name: pgbouncer
        ensure: present
        connectionLimit: 100
```

Application connects through PgBouncer, not directly to PostgreSQL.

## Schema Design Rules

### PII Storage
All PII columns are `BYTEA`, not `TEXT`. Application-level AES-256-GCM encryption.
The encryption key is injected from Kubernetes Secrets (never hardcoded, never in env for prod).

```sql
-- Correct
email_encrypted  BYTEA NOT NULL,     -- pgp_sym_encrypt or app-level AES-GCM

-- Wrong
email            TEXT NOT NULL,      -- NEVER
email            VARCHAR(255),       -- NEVER
```

### UUID Primary Keys
All tables use UUID primary keys. Generated by the application (UUIDv4 via `uuid.New()` for
non-principal records, UUIDv5 for principal identities). Never use `gen_random_uuid()` as a
default for tables where the application must control the UUID.

```sql
-- For records where the application controls the ID (appointments, slots, etc.)
id  UUID PRIMARY KEY

-- For audit records where DB-generated is acceptable
id  UUID PRIMARY KEY DEFAULT gen_random_uuid()
```

### Timestamps
All timestamps are `TIMESTAMPTZ` (with timezone), stored in UTC.
Never use `TIMESTAMP WITHOUT TIME ZONE`.

### Audit Schema Separation
The `audit` schema is separate from the `public` schema.
The application user (`app`) has `INSERT` only on `audit.*` — no `UPDATE` or `DELETE`.
A separate DB user (`audit_writer`) is used for audit writes.

## Migration Conventions

Files in `migrations/`:
```
000001_init.up.sql
000001_init.down.sql
000002_patients.up.sql
000002_patients.down.sql
...
```

Rules:
- Sequential 6-digit prefix. No gaps.
- `down` migration must fully reverse the `up` migration.
- Never `DROP` a column in an `up` migration — deprecate it first (add `_deprecated` suffix, stop writing to it, then drop in a later migration).
- Migrations run against all three jurisdiction clusters. They must be idempotent where possible (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`).
- If a migration needs to differ per jurisdiction (rare), use a separate file with a jurisdiction suffix: `000015_ca_mado_fields.up.sql`.

Running migrations:
```bash
# Up (apply all pending)
make migrate-up JURISDICTION=ca
make migrate-up JURISDICTION=us
make migrate-up JURISDICTION=br

# Down (roll back one step)
make migrate-down JURISDICTION=ca
```

## Local Dev — CNPG in kind

The Tiltfile installs the CNPG operator into the local kind cluster and creates a single-instance
cluster named `stdclinic-dev` in the `std-data` namespace. This cluster hosts all three
jurisdiction schemas in one database for simplicity:

```
Database: stdclinic_dev
  Schema: ca   ← Canadian patients
  Schema: us   ← US patients
  Schema: br   ← Brazilian patients
  Schema: audit
```

The `JurisdictionRouter` (`pkg/db/`) in local dev maps all three jurisdictions to the same host but
different schemas. This is the only environment where this pattern is acceptable.

## Backup & Recovery

CNPG handles continuous WAL archiving to S3. Recovery objectives:
- RPO: < 5 minutes (WAL archiving interval)
- RTO: < 30 minutes (CNPG point-in-time recovery)

Backup validation: a monthly automated restore test runs against a throwaway cluster and verifies
row counts. The test result is recorded in the `audit` schema of the restored cluster.
