# 0003. ConnectRPC inside the cluster, OpenAPI at the edge

Status: accepted
Date: 2026-11-08

## Context

The portals (BFFs, backends for frontends) call internal domain services, which are
never exposed to the internet. The product also needs a public interoperability API:
TGV criterion I06 asks for FHIR support, and FHIR is a REST specification. Both ogen
(OpenAPI) and buf (protobuf) were candidates.

## Decision

- **Internal**: services talk over [ConnectRPC](https://connectrpc.com), with schemas in
  `.proto` files managed by [buf](https://buf.build) (`buf lint`, `buf breaking`,
  `buf generate`). Connect runs over plain HTTP/1.1 or HTTP/2, so `curl` works, and
  `otelconnect` adds tracing.
- **Public**: `fhir-gateway` exposes a read-only FHIR R4 subset (Location, Schedule,
  Slot, Appointment, Practitioner) described by a hand-written OpenAPI document, with
  server code generated by [ogen](https://ogen.dev).
- **Messages**: NATS payloads are JSON defined by Go types, not by either schema
  language (see ADR 0008).

Layout: `services/<svc>/api/` holds the `.proto` files and generated Connect code, or for
`fhir-gateway` the OpenAPI document and ogen code.

## Alternatives

- **ogen everywhere**: one style, but internal calls would carry YAML schemas, and
  there is no `buf breaking`-style compatibility check.
- **gRPC everywhere**: browsers and FHIR clients expect REST and JSON, and gRPC needs
  HTTP/2 end to end.
- **The official FHIR OpenAPI document**: too polymorphic for ogen (choice types such as
  `value[x]`, extensions everywhere). A subset written by hand stays generatable.

## Consequences

- Two code generators (buf, ogen); both run in `make go-verify`.
- `buf breaking` against `master` protects internal compatibility.
- FHIR conformance is limited to the published subset; the matrix records it as partial.
